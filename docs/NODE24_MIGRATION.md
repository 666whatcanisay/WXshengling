## 后续迁移顺序与回退

1. 确认当前环境能创建Node24.11、CLI支持目标运行时，检查权限、网络、角色、环境变量、层及触发器是否与旧函数等效；不要把本地Windows24.22.2结果当Linux云24.11验收。
2. 在允许的新建/测试范围内，从生成目录创建带后缀的副本；函数安全规则另行核对，不能为跑通直接开放所有权限。原app/login/init保留，前端仍指向原名。
3. 用指定测试账号验证微信身份、只读数据和允许写入的目标/任务/奖励链，再验证失败/重复操作。init有初始化写入副作用，不把它当健康检查直接执行。
4. 联调通过后，再做前端函数名映射切换及对应版本发布；如失败，恢复原函数名映射和前端版本。迁移期间不删除旧函数、不改已有业务数据，也不把本地新功能捆入单纯版本升级。
5. 版本稳定后，继续发布/奖励可靠性收尾，再确定Agent接入范围。统一24消除版本差异，但不会自动提高函数时限或实现后台调度。

回退标签是代码定位点，不是云数据备份，也不能靠`git reset`回滚线上数据库。当前材料只覆盖代码、依赖声明与基本函数配置，真实身份、规则、网络及完整迁移仍需后续验证。
