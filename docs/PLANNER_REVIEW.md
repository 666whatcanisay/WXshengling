## 本轮效果

入口仍为“AI → AI审核师”，不新增页面。查看具体草案和用户要求后，可选择：

- **规则检查**：代码检查字段、有效日期、目标周期范围、单项时长/经验、同日预计总时长与明确每日投入；明确“只在周末”的表达遇到工作日会提示。问题定位到日期和稳定任务ID。
- **AI语义建议**：用户主动点击，服务器读取当前保存的模型配置，复用原HTTPS接口，针对具体要求和任务给出建议。首版不让模型作发布决定，不自动改稿或发布。
- **恢复结果**：重进页面自动读取已有记录；刷新审核结果只查记录，“读取最新稿”同步最新云端草案。本机有未保存修改时保留本机稿，提示先保存或恢复。

原规划师聊天、生成、编辑和发布流程保留。字段/日期的原发布校验继续执行；审核提示不成为额外的模型否决门禁。仍没有完整管理层运行或LangGraph生产集成。

## 模块与数据

| 模块 | 职责 |
|---|---|
| cloudfunctions/app/lib/plannerReviewRules.js | 纯规则事实、审核提示词和模型输出格式/任务引用校验 |
| cloudfunctions/app/lib/plannerReviews.js | 原生身份归属、版本核对、事务领取请求、幂等结果和明确失败 |
| miniprogram/utils/plannerReviewWorkspace.js | 当前版本、按钮状态、刷新、改稿失效和晚到/跨账号响应保护 |
| 原plannerDrafts / AI页 / cloudApi | 小幅扩展事务读取和接口衔接，继续复用可信草案 |

新增两个action：`getPlannerReview({mode, binding?})`只读，`reviewPlannerDraft({mode, binding, request_id})`主动检查，mode为rules/ai。身份只取`cloud.getWXContext()`，不信任事件内openid、模型或密钥。

记录继续放在既有ADMINONLY的`ai_plans`，`kind=planner_review`。确定性记录ID包含账号、草案ID、revision、fingerprint、requirements_revision、rules_version及mode；不新增集合、权限或依赖。审核记录不用旧生成结果的result字段，避免被当成可发布生成来源。

同一版/同一规则的成功结果缓存，改模型配置不会悄悄替换已完成结论；显示实际调用的provider/model。修改草案后生成新版本，旧结论失效；跨设备修改也在服务器的事务内重新核对当前head，不采纳客户端自报事实。界面旧版本建议隐藏，不写“审核通过”。

## 费用、失败与限制

- 2026-11-10 本地修复：运行记录的确认窗口为 60 秒。中断后刷新可查看恢复资格；旧编号始终只查记录，新编号才可手动重试。迟到回包不能写回过期或已接手的记录。上线需配套上传 `plannerReviews.js`、`coachService.js` 与共用的 `modelRunLease.js`。

- 规则检查不调用模型；AI审核只在主动点击时发起。现有配置由当前账号保存的供应商密钥提供，费用计入对应供应商账户，本轮不更改费用承担方式。
- 事务只领取请求与保存状态，模型调用在事务外。同版并发/重复请求返回running或缓存；不会因数据库事务自动重试再调模型。失败后仅新的显式请求可重试，旧request_id即使晚到也不会再调模型，最多3次失败尝试。
- AI结果必须是有效JSON、限定字段和已存在任务ID；无效/空结果写failed，不伪造成功、不自动重试或套模板。不强制新增供应商参数，兼容当前OpenAI风格接口；严格验证返回结构。
- 此处模型请求增加18秒绝对截止，保留当前30秒函数配置给数据库收尾，原其他调用默认行为保留。超时请求仍可能在供应商侧计费，手动重试可能另计费；这不是账单意义的恰好一次保证。
- 若模型调用后云函数崩溃或最终数据库写失败，保留running。刷新只查询，首版不做自动超时抢占，避免不确定结果重复计费；真正卡住需管理侧核查，不能承诺自动恢复。
- 只传结构化要求、短来源片段、草案和规则事实，不传完整聊天/Key；不写模型Key到结果、记录或日志。沿用原适配器的错误遮蔽。
- 时长是**预计值**。空预算、无法换算的值和缺时长明确未知；日期覆盖不是目标达成。当前中文规则提取仍是有限表达识别，用户需核对“审核依据”，复杂预算/其他现实条件交给语义建议并保留不确定性，不宣称穷尽所有约束。本轮顺带修正每日小数时长识别，0.5小时可正确换成30分钟；已经保存的旧草案不会自动重写。
