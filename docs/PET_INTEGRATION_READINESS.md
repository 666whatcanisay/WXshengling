# 宠物伙伴接入依据（源码核查，2026-11-07）

本文件供下一阶段讨论，不实现宠物联动、不增加采集或新集合。仅说明代码可提供什么；未读取真实云数据，不保证每条旧记录完整。

## 已有数据与可用程度

| 来源 | 源码确认已有 | 关联及限制 | 后续候选用法 |
|---|---|---|---|
| 目标与任务 | `goals`目标ID/周期/状态；`tasks`账号、goal_id、date、completed、estimated_minutes、completed_at | goal_id关联目标，按北京时间业务日取数；旧完成记录可能没有登记时间，预计时间不等于实际时间 | 复用教练事实口径，谈论“已登记完成”和待办；不推断现实成效 |
| 教练反馈和复盘 | `ai_plans`中coach_feedback/coach_report；目标、日期、反馈版本、事实指纹及报告引用 | 用户自述与客观记录分开；反馈或任务改变后只使用当前指纹结果 | 让宠物温和呼应用户已保存的反馈；哪些文字可共享仍待用户确认 |
| 草案和协作 | 云草案版本、审核绑定；forest_state与adjustment_state的运行/步骤/版本/回执 | 新目标草案与已发布目标不是同一身份，不能按标题匹配；未发布内容不能当正式任务 | 经准确引用区分“正在准备计划”“已发布”“调整已应用”，复用现有回执而非新增模型判断 |
| 成长日志 | growth_logs的账号、source、reason、xp_change、created_at；新打卡日志ID含任务ID | 常见日志缺结构化task_id/goal_id/pet_id；旧记录ID也不统一。不能解析自然语言reason硬关联某目标或宠物 | 首版可给有限的账号级近期摘要；需要精确实体事件再另定结构化字段与兼容方案 |
| 宠物当前状态 | pets的物种、阶段、属性、亲密度、心情等；chat_context含物种/阶段/属性/性格说明和growth_records | 按宠物ID与账号读取，过滤删除/未孵化状态。chat_context不等于完整聊天历史；growth_records的历史覆盖未验证，宠物心情也不等于用户心情 | 构建角色设定，不据字段名假定已有长期记忆 |
| 宠物事件 | pets.pet_events内事件ID、trigger_type、triggered_at、标题、内容、read；连签/成长相关入口有调用 | 是特定里程碑事件，不涵盖所有喂养/玩耍；updated_at是混合修改时间，不是准确上次喂养时间 | 引用带事件ID的里程碑；不宣称存在完整行为流水 |
| 当前宠物聊天 | AI页sendChat使用关键词/固定回复，消息保存在页面messages；尝试调用petInteract，通用云端aiChat只代理传入消息 | 当前聊天没有自动带入目标/复盘，也没有已实现的宠物云聊天保存链；连续发送时消息快照及旧回调需在聊天改造阶段处理 | 保留现有入口，后续再确定是否接当前模型、历史长度及费用策略 |

## 下一阶段建议（尚未实现）

1. 首版以“当前宠物角色 + 用户指定的一个目标 + 有上限的近期真实事件摘要”为候选，复用现有云端归属校验，不直接给客户端开放数据库。完整扫描与费用上限需在范围确认后定。
2. 共享内容保留来源引用：目标ID、日期窗口、反馈/草案版本或报告指纹、宠物/事件ID。缺少关联就降为账号级或未知，不按标题、自然语言或时间接近强行匹配。
3. 宠物聊天提到偏好/心情时，先作为候选用户自述；用户明确确认后再考虑传给规划/教练，带来源、确认时间和可撤回入口。不要自动变成硬约束、诊断或任务修改。
4. 聊天作为独立陪伴入口，管家继续协调规划/审核/复盘。首版不需要给每个角色各建一个LangGraph或长期记忆系统。

需用户集中决定的是：聊天模型及费用边界、保留多少历史、允许共享哪些内容、是否允许主动提及近期行为。本轮没有替用户作这些决定。

## D044 · 宠物首版讨论方案（2026-11-07，助手建议，未授权实施）

用户要求停止全面盘点，保留自然陪伴、真实行为联动和偏好反馈的原始目标。下面只讨论本轮值得做的增量，不将历史展示清理、统一成长数值或重做规划师设为前置。

### 推荐体验与接入位置

- 保留AI页原宠物聊天入口和森林风格，小幅补充当前宠物/可选关联目标、上下文范围、历史清除及共享偏好入口；不新增角色或独立大页面。默认候选为一只已孵化宠物，可切换；多宠物历史隔离，无可用宠物时如实说明状态。
- 聊天可自由谈感受和日常，不强迫讨论任务、不强制关联目标。回复结合宠物设定与近期对话，必要时呼应真实近况；不每次都复述统计或催打卡。
- 用户主动选择一个目标后，可参考近7天登记事实/已保存反馈、当前有效复盘，及准确关联的计划发布/调整回执。用“已登记完成”描述任务，区分草案/发布/应用，不按标题猜关联；无记录或读取失败时说明缺口。
- 喂养联动首选宠物页已有`petInteract(feed)`。建议在其成功更新时同次保存最近互动的类型、时间及请求引用，供后续聊天读取；只表示最近一次可追溯动作，不宣称完整流水。背包饲料的消耗/写宠物/日志为分步流程，暂另列；若纳入首版，需另明确局部收口范围，不扩成整套成长重构。
- 偏好例子：“这周晚上容易累，想少安排晚间任务”。建议聊天生成可编辑的偏好候选，用户选择是否供规划/教练参考，能更正/撤回，区分本目标/通用范围和临时/长期有效期。具体确认交互尚待讨论；不自动成为硬约束，不直接修改任务。

### 技术首选及取舍

沿用原生微信前端、现有HTTPS模型适配和Node24业务后端，新增独立宠物服务/工作区及最小上下文读取；森林管家继续复用现有LangGraph。首版单次聊天通常只需一次模型调用，建议用同次结果返回自然回复及可选偏好候选，不每条追加一轮记忆提取或全角色协作。

| 选择 | 推荐候选 | 代价或保留边界 |
|---|---|---|
| 模型 | 复用用户当前已保存、已验证可用的供应商配置，宠物使用独立提示词 | 不强制换模型或增加SDK；聊天自然度需少量明确场景实测，不保证提示词就达到体验参照 |
| 对话记忆 | 云端保存有上限的近期对话，按账号/宠物隔离；例如保留20轮、每次最多带入最近10轮，并另设字符/输入预算 | 数字仅供讨论；历史存储量、每次发送量与保留期限分别决定。超过范围不假装记得，可清除；相较仅本机保存，多了云读写与删除逻辑 |
| 长对话 | 首版按窗口截取，暂不每轮调用模型摘要、不引入向量库 | 成本和实现范围较小，久远聊天可能遗忘；经用户认可的偏好单独保留，不依赖窗口碰巧包含 |
| 行为上下文 | 优先直接复用任务事实、确切回执、宠物里程碑及上述最近互动元数据 | 不解析日志自然语言强行关联，不先建设全量事件总线；读取设范围/上限，避免每条无条件重复整套教练扫描，新鲜度与刷新策略须明确 |
| 共享偏好 | 小型、带来源/范围/有效期和版本的记录，经选定确认方式供规划/教练按需读取 | 不把全量私聊传给其他角色。当前明确要求优先，矛盾时核对；修改/撤回后新输出不再使用，旧草案/报告不被静默改写 |
| 宠物图编排 | 首版先使用独立受控服务，保留接入管家的接口 | 现有LangGraph仍管理主协作；等陪伴出现多步工具委派需求时再讨论复用图，避免为单轮回复复制整套运行记录 |

官方依据：DeepSeek[多轮对话说明](https://api-docs.deepseek.com/guides/multi_round_chat/)明确Chat Completions需由应用传入历史；LangGraph[记忆说明](https://docs.langchain.com/oss/javascript/langgraph/add-memory)区分线程内历史、跨会话记忆及历史裁剪。两者不自动赋予现有宠物长期记忆。上述轻量服务首选是结合当前单次调用/原生SDK的项目判断，未安装或试运行新方案；最新文档示例不直接套进本项目已固定的1.6.1版本。

### 范围内必须处理的可靠性

- 宠物专用后端按真实微信身份读取角色/目标/历史并组装提示，不信任客户端自报经历；原aiChat可复用模型适配，不直接当具备宠物上下文和持久化的成品接口。
- 发送使用稳定请求ID，服务端领取/缓存结果，客户端处理连续发送、换号/换宠物、离页及晚到响应。网络未知先查原结果，不自动重发模型；失败不冒充模型成功，不承诺供应商账单恰好一次。
- 聊天回复与原有互动奖励分离核对。是否保留每次聊天的旧互动收益须先讨论；若保留，新增调用须防止读历史、查询或模型重试再次结算，不把奖励数额交给模型，也不借机统一全部成长规则。
- 偏好若进入规划/教练，必须带来源和版本参与要求绑定/复盘指纹，避免共享内容已变化却继续复用旧结论。撤回不自动改已发布任务；应用仍沿原确认接口。
- 新调用逐项核对handler、cloudApi解包后的返回形状和具体成功字段；不假定所有接口均返回同一种封装。

### 候选实施分段与完成标准

1. **自然聊天＋真实近况**：保留入口，接有限历史与当前宠物/可选单目标、明确喂食来源；验证连续聊天/重进恢复/换宠物隔离/缺数据/失败及重复请求。用“刚登记完成任务”“刚确认喂食”“今天很累”几个短场景检验回应准确且不过度催促。自然度另需用户实测，不用结构断言代替。
2. **偏好进入主协作**：可查看、编辑、确认/撤回共享偏好，规划/教练明确展示参考来源并处理版本失效；用同一条已确认偏好在两种角色中实际影响建议，撤回后新请求不再采用。两段均为首版路线建议，各段开发前对齐，不能把本次讨论当连续实施授权。

当前待讨论：云端还是仅本机历史、历史窗口/保留期限、现有模型费用与单次输入输出上限、是否主动提及近况、偏好共享确认方式，以及聊天是否保留原互动收益。本轮只形成方案，无新功能、真实云读写、模型调用、部署或新测试结果。

## 2026-11-08 · 以一次可续的陪伴对话为首版（候选）

本轮用户明确要求先存档、暂缓宠物聊天开发，优先优化 AI 自律森林工具箱。以下仍是恢复讨论时的候选方案。

1. **先做好已有入口。** 「AI → 宠物聊天」顶部显示当前宠物，可切换；首次只有一只可聊天的宠物时直达，多只时选一次，之后恢复上次选中。用户随时能自由聊天。「聊聊今天」由用户主动点开，按需读取所选目标近况，不占普通闲聊的输入预算。任务首版使用有时间的登记结果。
2. **先保存有限历史，再试显式续聊。** 推荐近期历史保存最多 7 天且不超过 20 轮，每次模型输入先用最近 6 轮并设总预算。下一阶段加入一条由用户确认的「留到下次」，保留来源、适用宠物、有效期和状态，可编辑、完成或撤销。保存策略是候选，需在实施前确认。
3. **聊天和养成分开。** 当前每条聊天会尝试对列表首只宠物调用 `petInteract('chat')`。符合条件并成功时，后端按缺省分支结算 5 宠物经验和 2 亲密度。候选取消按消息次数结算；如需保留陪伴奖励，单独定义按所选宠物结算的事件及去重规则。喂食联动在后续先补森林按钮对应宠物的成功凭据。
4. **用现有前端和模型适配做一条完整链路。** Node24 云端按账号和宠物授权，使用稳定消息 ID 保护重复确认，按宠物恢复历史。首版一条回复最多一次模型调用。明确显示等待和失败，同一次发送超时后优先查已受理结果。
5. **跨角色共享放在末段。** 先让用户在宠物侧验证记忆确实有用，再把经单独确认、可撤回的偏好供规划或教练参考。当前草案与复盘的来源、版本及用户确认流程继续作为协作依据。首轮验收重点为普通闲聊、近况事实、离页重进、切宠物、延迟响应和失败恢复。

## 2026-11-08 · 恢复设计讨论（首版候选，未授权实施）

### 重新核对后的现状

- AI 页现有对话是关键词或随机短句，旧消息只存页面状态，发送路径没有接通用模型代理。宠物标题和奖励分别取列表首只。离线以生产 Page 模拟连发两条并逆序返回，最终仅剩一条用户消息及一条回复，两次旧奖励调用均指向第一只宠物。旧界面写着每轮增加亲密度；当前成功的 `petInteract('chat')` 走缺省 5 宠物经验和 2 亲密度，未孵化或失败时没有该回执。
- D054 本地代码给背包使用记录加了 `item_name`、`pet_id`、`created_at`，和扣库存及宠物变化一同提交。普通/高级饲料可按当前账号、宠物、动作和日期读回。森林直接互动的 `interact_feed` 仍缺该宠物的结构化引用；旧日志也不猜归属。D054 仍有云端及真机验收边界。
- `tasks.completed_at` 是登记时间，`tasks.date` 是计划日期。聊「今天刚完成」按北京时间读取前者和真实完成标志。缺登记时间的旧记录只说明已完成，不说何时。规划师、教练与管家有各自的版本和输入，普通闲聊不带入它们的稿件、报告或私有反馈。

### 首选体验

- 保留「AI → 宠物聊天」及现有森林样式。顶栏只展示当前宠物、头像/立绘和换宠物入口。只有一只已孵化宠物时直达，多只首次选择、以后恢复。每只宠物独立保存聊天和草稿，释放后停止新聊天，历史处理在上线前说明。宠物立绘用现有分包及占位组件，小尺寸只播放少量已有动作；所有等级同等支持对话和记忆，S 级差异沿用现有饰件。
- 人设用一套陪伴底线，加当前宠物名、已有性格和少量物种语气提示。回复优先接住用户这句话，可用短句或一个自然追问。用户累时可以只陪伴，是否谈任务由用户决定。规则规定不得声称观察到未经记录的事，不自动改任务、不后台催办。心情和宠物语气属于对话内容，不能覆盖真实记录或授权范围。
- 聊天输入为主，辅助只留「聊聊今天」。点开可查看本轮允许引用的近况，可选单目标；读到真实登记或这只宠物的饲料回执才提供对应事实，显示日期和来源。普通闲聊读角色和近期聊天，业务近况按需读取。首版按消息取消旧奖励作为建议，避免把聊天变成刷亲密度；养成动作走森林原入口。
- 推荐讨论参数为短历史最多 7 天且最多 20 轮，每次先带最近 6 轮，再按输入预算裁剪。显示保存和模型发送范围，提供清空。期限以能实际清理已过期记录为验收条件，删除/换号/换宠物后在途旧回复不得写回当前会话。平台备份与供应商保留口径需在上线前核实。

### 最小技术路径和阶段验收

1. **先通一只宠物的真实多轮聊天。** 沿用原生微信页、Node24 云函数和已有 HTTPS 模型适配。独立宠物服务只接宠物 ID、消息、请求 ID 和允许读取的上下文范围，后端按微信身份重新授权并组装角色与近期对话。以账号、宠物、会话代次和请求 ID 去重；每只同一时间一条请求，保留在途草稿。收不到回执先查原请求，明确失败才由用户重试。一次回复一次模型调用，进入页面、切换、读历史和查回执均不调用模型。沿用 30 秒云函数边界，在内部留出写回余量；记录延迟分布、调用次数和可获得的 token 量，不采集聊天正文到诊断日志。
2. **在同一阶段验收真实近况，喂养按依赖分批开。** 先核对已登记任务、空数据、失败和缺时间旧任务。确认 D054 在对应环境生效后，再接带宠物 ID 的背包饲料；森林直接喂食的准确关联另行评估。用两只宠物验证串线，连续发送和逆序响应验证消息完整，清空中有在途请求验证不复活。自然度用闲聊、疲惫、庆祝三个真人短场景看是否贴合、是否每轮都催任务。事实或身份串线作为验收阻断。
3. **再试一条由用户确认的「留到下次」。** 只记一条可编辑、完成、删除的待续事项，带适用宠物、来源与有效期，保留较新更正。稳定后才讨论共享偏好；用户主动确认哪些条目可被规划师/教练参考，原聊天保持隔离。参考 LongMemEval 的记忆更新、时间与无证据应答题型做项目自己的对照。

外部参考：[DeepSeek 多轮对话](https://api-docs.deepseek.com/guides/multi_round_chat/)说明历史由应用传入。[鱼的记忆](https://github.com/Yuuyuko-uu/dsh-fish-memory)展示带时间和按需注入，[大肥鱼 B 站插件](https://github.com/Alterssss/dsh-bili-whale)展示人设与行为规则分层。[LongMemEval](https://arxiv.org/abs/2410.10813)提供 500 题评测。项目首版取短历史、明确来源和少量有用事实；每条聊天的模型预算、旧奖励是否取消及云端历史开关待讨论。

## 2026-11-08 · 角色卡与聊天节奏样稿（设计候选）

- 用户希望对齐大肥鱼的自然聊天方式，能一眼辨认当前宠物、看完整资料，并按宠物微调相处方式。已有森林宠物资料和性格期望用作角色卡来源。角色档案与相处设置分开，同一只宠物的数据来源一致。小栗和麦芽是界面示例，样稿中的对话与设置仅用于演示。
- 对齐对象是几个公开社区实现。[鲸鱼娘预设](https://github.com/linsport/dsh-whale-persona)用背景、习惯、看事情的方式和语言例子给角色一致性；[鱼之魂](https://github.com/Britneycode/dsh-fish-soul)有可编辑角色卡、语境与心情驱动的表达、QQ 群合批以及可纠正记忆；[dsh-fish](https://github.com/ssamurias/dsh-fish)把主动发言设为可选且要求有由头。这里将群聊合批借用为微信私聊的短窗口，不把两种场景视为同一实现。拟用森林的眨眼和摆尾做轻回应，动作仅作展示。
- 「相处设置」候选项：称呼、语气、等我说完或及时接话、疲惫时先听或给一点建议、是否在前台进入时偶尔搭话，以及折叠的消息长短、小动作、回提约定、补充偏好。可用同一句话试听，保存只作用于这只宠物的下一轮；历史保持原样。预设、用户原有性格期望、后续微调分层存储；恢复默认只撤销微调，保留森林原资料和聊天记忆。
- 连发消息先即时显示，按当前账号、宠物和会话聚合已提交的短句。候选默认等约 0.8 秒，上限约 1.3 秒，明确提问与及时模式直接进入回复，真实等待才显示状态。服务端以一个批次请求 ID 一次模型调用，按语义显示一段或少量气泡；闲聊可用轻动作或短句接住，明确提问保持可见回应。「先听我说」期间保留消息，用户可主动结束倾诉再邀请回应。旧回调不覆盖后续消息或其他宠物。
- 偶尔接话默认关闭。开启后，仅在用户进入聊天且有已确认的待续事项或明确授权的真实近况时考虑一次，前台静默窗口和同一事项防重复。记忆保留明确的确认、有效期和纠正方式，角色卡和临时情绪分开。无需虚构宠物的经历来填空。
- 建议先验收三连发不丢、明确提问有答、疲惫时先听、记忆纠正、切宠物隔离、调节前后同一句话确有差异。样稿浏览器检查只验证界面控件和示例文本，不等于模型表达已通过。
