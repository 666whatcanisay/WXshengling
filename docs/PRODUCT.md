## 候选作品定位（助手建议，未定稿）

沿用产品名「AI自律森林」，建设能帮助用户制定目标、执行任务、回顾表现和获得宠物陪伴反馈的成长管理小程序。

依据 2026-11-04 用户提供的老师讨论，面向有学习、运动、阅读等日常目标与自律需求的人群，不限定大学生。可选取具体领域作为开题案例，不据此宣称已覆盖所有人群和场景。

当前助手首选题目：《基于分层多智能体协作的个人自律管理微信小程序设计与实现》，尚未由用户或老师定稿；按 D012，题目和毕设材料不再作为当前优先推进事项。产品名继续用「AI 自律森林」。此前「AI辅助目标管理与宠物养成系统」「多智能体协同目标管理与宠物陪伴系统」保留为早期讨论背景。

希望形成的体验：用户说清目标和约束，系统给出可编辑的计划；确认后成为实际任务；执行产生真实记录；复盘给出有依据的调整建议；宠物成长让努力有可见反馈。

设计理由：规划帮助开始，任务帮助行动，分析帮助调整，宠物提供持续反馈。这些是设计动机，不能在没有用户研究的情况下声称已证明提高自律能力。

## 普通代码与 Agent 的边界（候选）

| 工作 | 实现建议 | 理由 |
|---|---|---|
| 身份、权限、数据读写、打卡、签到 | 后端业务代码 | 确定性规则，需要稳定与可验证 |
| 经验、成长池、道具消耗、进化、奖励 | 后端规则计算 | 模型不决定资源余额或奖励金额 |
| 完成率、日期统计、图表 | 数据查询与代码聚合 | 数值应可追溯，模型不能编造 |
| 番茄钟、简单抽签、静态问卷 | 轻量本地逻辑 | 不需要模型判断 |
| 根据用户目标与执行情况组织业务 Agent | 上层管理 Agent（当前候选） | 结合上下文确定子任务、委派、反馈汇总与后续调整；角色数量与具体职责待定 |
| 理解目标、澄清约束、拆分任务 | 规划 Agent | 需要自然语言理解和个性化规划 |
| 解读执行记录、提出调整 | 分析/教练 Agent | 结合证据与用户反馈给出建议 |
| 个性化宠物对话 | 可选陪伴 Agent | 结合性格和近况表达，基础互动继续用规则 |
| 应用新计划或调整 | 用户确认 + 后端校验与写入 | 建议与真实数据变更保持明确边界 |

## 分层多 Agent 架构（方向更新，具体分工待定，尚未实现）

2026-11-04 的新背景见 D011、D012：上层管理 Agent 组织下层；下层按工作分工已由用户确认，学习、运动等作为支持领域的安排仍为建议，具体角色与数量继续讨论。以下职责为可复用此前方案的候选，不是本轮已确认的最终架构。

- 上层管理 Agent（候选）：结合用户目标、时间预算和近期执行情况，确定待处理问题、选择下层 Agent、组织反馈并汇总结果；应能记录委派依据与输入输出，不能仅以固定调用顺序证明智能管理。
- 确定性执行与校验层（不是 Agent）：继续处理权限、参数/资源校验、调用上限、失败处理和受控写入，与上层管理 Agent 分开。
- Planner（规划 Agent）：读取目标、期限、基础、时间预算，输出阶段和任务草案（结构化 JSON，含天序号、预计时长、阶段归属）。
- Critic（审核 Agent）：检查 Planner 草案是否违反用户约束，输出通过或带定位的修订意见。硬约束（总时长超载、单任务时长、任务数）由代码算术判定，模型只负责合理性与可执行性判断。修订最多 1 轮。
- Analyst（分析 Agent）：读取代码算好的统计与关联记录，输出带证据的观察、限制和不确定性；无历史时明确冷启动。
- 宠物陪伴 Agent（非任务型）：读取宠物性格、成长阶段、亲密度与近期真实近况，生成回复。边界待定（D007）。

两条链路：

1. 新建计划（候选分层衔接）：上层明确目标与约束 → Planner → Critic →（不通过则修订 1 轮）→ 上层汇总 → 用户编辑确认 → 受控落库。
2. 执行后复盘（候选分层衔接）：上层组织 Analyst 读取真实统计 → 形成复盘与调整建议，必要时委派 Planner → 用户确认 → 只变更未来任务。

协作要有实际的数据依赖：规划草案交给 Critic 审核，审核意见能影响修订；复盘结论能进入调整计划。不能用一次模型回答伪造多个 Agent 发言或协作进度。

不同 Agent 可以共用一个模型，但应有独立职责、输入输出约定、受控数据工具和运行记录。仅改系统提示词并加角色名，还不足以证明已实现完整 Agent 协作。

**执行方式（技术约束与最新建议）**：现有app仍Node16/30秒，`aiDoGenerate`内同步调用模型。Node24隔离回归已通过，官方支持列表有24.11，助手现建议自管开发/后端/Agent以24为统一目标；尚未迁移。统一后版本差异不再强制独立部署Agent，保留编排与业务代码模块边界，服务是否分离按超时、后台推进、包体与维护成本评估。前端查询状态不代替后台执行机制。详见 `LANGGRAPH_EVALUATION.md`。

**运行记录 `agent_runs`**：每条记录角色、输入摘要、输出摘要、耗时、状态、是否走了模板兜底、修订轮次。这是「可观测性」的证明依据，也是答辩时最直接的证据。

工具候选：读取目标、读取近期任务统计、读取情绪摘要、保存计划草案、提出调整。实际写入必须继续由受控业务接口完成。

不默认每轮全员参与。简单对话走短流程；生成计划才规划与审核；复盘才分析与教练。

## 交付范围与验证

候选演示：新用户提出目标 → 补齐必要信息 → 规划与审核 → 编辑确认 → 创建任务 → 打卡获奖 → 宠物成长 → 根据记录复盘 → 预览并确认调整。

验证至少覆盖无历史、有记录、约束冲突、模型失败、重复点击。可比较单规划流程与协作流程的约束满足率、任务可执行性、耗时；没有对照证据时不声称多 Agent 一定更好。

测试数据应明确标注为测试场景，不能当作真实用户效果研究。候选主题、流程和评价口径需要后续迭代。
