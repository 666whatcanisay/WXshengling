用户随后询问整个项目统一Node24。最新建议以**自管的开发/后端/Agent统一24**为目标，替代下文初次调查的“业务16 + 独立Agent22”优先方案；小程序页面使用微信JS环境，开发者工具内置Node也不能靠项目配置直接替换。尚未执行正式升级。

- 下载官方便携Windows Node24.22.2并核验SHA256，不替换系统Node、不改全局PATH；41项业务隔离回归、35个生产JS语法检查、TypeScript构建及15项图流程通过。现有SDK可加载三个真实云函数入口，未执行handler或真实网络业务。证据见 `audit/node24-compat-20261104.json` 与 `audit/langgraph-compat-node24-20261104.json`。Node22基线证据另行保留。
- 只读重查app/login/init仍是Nodejs16.13。CloudBase[更新配置API](https://cloud.tencent.com/document/api/876/137946)明确runtime创建时指定且不支持修改，不能只改package.json/engines或配置就算云端升级。建议新建Node24副本、匹配配置和依赖、联调后切换并保留旧函数回退；不先删除现有函数。
- Windows24.22.2通过不等于Linux云24.11及其微信身份/数据库/存储/网络链已验收。正式迁移须先核实账号地域可用性、平台确切补丁、部署依赖及回退；本地有尚未上线业务变更，需要明确迁移使用线上基线还是同时发布本地变更，不能混为单纯升级。
- 统一24后，运行时版本差异不再强制Agent独立部署。继续保留代码模块和工具边界，是否单独服务由超时、后台执行、依赖大小和维护成本决定。升级Node也不会自动改变当前30秒限制或实现多Agent。

建议下一轮范围为版本配置与云端迁移准备，随后在明确测试/部署范围后新建副本验收切换，再回到发布/奖励可靠性与Agent接入。当前调查不授权删除函数、改变全局环境或整套架构。

## 推荐与反思

初次调查首选为 **LangGraph.js + 独立 Node.js 22 Agent 模块**，现由上述Node24统一目标调整部署建议：用状态图组织规划、审核、有限修订和用户确认，业务模块负责身份、任务、奖励等。其价值是流程可恢复、职责可拆分和后续多目标扩展；不是套上框架就成为多 Agent。下文保留初次实验与取舍依据，最新部署判断以上述补充为准。

此前考虑直接嵌入 app 或靠前端轮询逐步推进，现根据真实 Node.js 16 / 30 秒部署和当前依赖要求调整：不把新编排依赖直接塞入旧函数。前端可以查询状态，但关闭页面后仍需执行的工作必须有服务端执行机制；框架本身不延长超时，也不替代队列。

独立模块是代码与部署边界，不一定要另买环境或起容器。先核实同环境 HTTP Agent 云函数能否满足 Node 版本、时限、包体和鉴权；能满足则优先，以减少运维。长连接/自定义运行时需求明确且函数不满足时，再选 CloudBase Run。尚未核实本环境可用版本、配额、计费或真实端到端调用，不把 CLI 帮助中的示例当部署成功。

## 已核实事实

| 项目 | 本次证据 | 含义 |
|---|---|---|
| 现有 app 云函数 | 云端只读详情：Nodejs16.13、30 秒、256 MB | 不适合直接安装本次当前依赖并增加串行模型步骤 |
| LangGraph.js | 1.6.1，包 engines >=18 | 根包最低要求不代表全部依赖最低要求 |
| @langchain/core | 1.3.4，包 engines >=20 | 与现有 Node16 不兼容；迁移文档还建议 Node22，因此建议独立新模块用22 |
| 腾讯适配器 | @cloudbase/agent-adapter-langgraph 0.0.24 | 实际导出 CloudBaseSaver，可复用 NoSQL 路线，无需先增设 Postgres/Redis |
| 本地实验 | Node22.16.0；TypeScript 编译和15项检查通过 | 核心图与保存适配器在隔离条件下可运行，非生产接入验收 |
| 依赖成本 | 实验含适配器与开发依赖，锁文件590项、Windows实际565个包条目；node_modules约433 MB | 不是生产压缩包大小或冷启动实测；不能据此断言平台一定超限，但不宜整套直接拷入旧函数 |
| 安装兼容性 | mem0ai 与 Anthropic SDK peer 版本警告，安装脚本已禁用 | 成功导入不等于全部传递功能可靠；正式采用需收敛依赖和验证产物 |

## 实验覆盖与边界

源码在 `experiments/langgraph-compat`，机器可读结果为 `audit/langgraph-compat-20261104.json`。主要流程为确定性规划 → 审核 → 至多一次修订 → 确认/拒绝 → 模拟应用。

15 项检查覆盖审核修订上限、确认暂停/恢复、拒绝不应用、确认节点重入、完成后空输入不重复应用、不同线程状态、临时失败重试、永久失败显式抛出、仍不合格时终止、独立进程恢复、其他 userId 无法读取已有线程、检查点列表/删除、CommonJS 入口导入。

跨进程测试使用真实腾讯 CloudBaseSaver，数据库为本地 JSON 文件替身。未连接真实 NoSQL，也未验收其事务、索引、文档大小、权限、并发写入、网络故障或 ID 约束。仅验证过滤读取不等于完整多租户安全。正式 userId 必须来自服务端可信身份，线程归属也必须校验。

恢复会重新进入 interrupt 所在节点，本地计数也证实了这一点。发布和奖励仍需业务幂等控制；单次测试不重复应用不等于任意故障下都只写一次。实际模型质量、上层管理判断、Token、延迟、SSE/小程序客户端均未验证。使用确认对象 `{ approved: boolean }`，本次直接传 false 恢复出现 EmptyInputError，记录为该版本实验现象，不上升为通用规则。

## 其他路径比较

| 方案 | 当前取舍 | 状态 |
|---|---|---|
| LangGraph.js 独立模块 | 显式状态与恢复适合规划/审核/确认，未来可加模型管理节点；复用既有业务 | 首选建议，本地核心实验通过 |
| 轻量自建状态机 | 短期依赖少，但检查点、恢复、修订控制等需要自维护；若部署约束阻挡框架可作为备选 | 仅比较，未新增业务实现 |
| Mastra | 提供 Agent、工作流、存储等一体化能力；当前已有 UI/数据库/业务，首轮引入面更大；@mastra/core 1.82.0 元数据要求 Node>=22.13 | 官方文档/包元数据调查，未安装、未实测，不作为首选 |

腾讯完整 AG-UI 服务适配、Agent UI、长期记忆与观测平台不打包作为本轮必选。CloudBaseSaver 虽已本地跑通，仍需验证正式依赖产物和真实数据库；先不为了规避依赖而复制一套第三方保存器。

## 后续建议（待阶段对齐）

1. 先完成业务可靠性一批：AI计划重复发布/中断恢复、任务并发重复发奖、管理员身份兜底。用现有云函数与数据库的请求去重、条件写入/必要事务实现，先本地回归，真实写入与部署另列范围。验收以重复/失败重试不新增重复任务、不重复奖励、无关用户不能管理为准。它同时给未来 Agent 提供可靠工具。
2. 接入前集中讨论一次：上层能判断/委派什么、首版下层职责、模型与成本来源、如何确认计划，以及独立模块实际部署边界；据此形成最小单目标 Agent 竖向流程。先核实函数运行时、包体与可信身份传递，再决定 HTTP函数或云托管。
3. 首版单目标协作打通后，再接真实执行记录、主动复盘与未来任务调整，最后扩到多目标协调；不是已确认的固定整套排期。
