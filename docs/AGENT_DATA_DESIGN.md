## 1. 先区分已有数据、用户自述和候选规则

Agent使用的数据来自：用户在页面/聊天中明确提供的内容、后端保存的业务记录、代码计算的统计、模型建议与假设。四者必须标明来源。LangGraph传递这些结构化输入与结果，不会自动获得未采集的数据，也不替代数据库或用户反馈。

系统中的“完成”首先代表用户打卡登记，不能证明现实中的活动已被客观测量；用户自报困难是反馈，模型从低完成率推测“因为太难”仍是假设。

## 2. 规划师：保留聊天采集，补齐可信状态

### 当前已存在

- 用户通过原规划师聊天表达目标、动机、周期、每日投入、基础水平等。前端goalContext有what/why/deadline/dailyTime/level/constraints六项。
- 普通模型聊天aiPlannerChat只接收页面最近20条消息和规划师系统提示词；当前没有自动读取目标/历史任务/心情/用户长期偏好的调用链。
- 前端慢路径尝试从AI回复抽取目标、周期和每日投入；快路径/降级路径也用正则。因此用户原话、模型建议和已确认信息尚未可靠分开。
- aiStartGenerate把当时planState和消息快照写入ai_plans；页面提交planState包含前五项，没有单独传constraints。生成时模型仍可从完整消息快照看到聊天中的约束，但不保证被可靠识别和遵守。
- aiDoGenerate输出goal和tasks；任务草案含标题、预计分钟、经验、阶段和日期序号。前端把它转为可编辑的日期任务。
- 发布后goals/tasks保留周期、阶段、任务日期等，但publishAiPlan创建的goal.description为空。不能只读发布后的goal.description就宣称取回完整动机/预算；必要时沿发布来源找生成快照，缺失则询问用户。

### 建议最小补充（未实现）

继续用原聊天采集，不另加一套强制问卷。把用户原话提取为带来源的目标上下文：字段值、来源消息、明确表达/待确认假设、更新时间。模型提出的“30天/每天20分钟”先视为候选值，不自动成为用户事实。

初次规划主要靠当前目标与约束即可；有历史后，服务端按需附同目标或相关任务摘要、用户明确偏好。已发布目标可从目标详情选择后传入引用；不能默默把用户所有目标和聊天全发给模型。

## 3. 审核师：草案从哪里来

| 草案来源 | 当前基础 | 待补的交接 |
|---|---|---|
| 规划师刚生成的草案 | aiDoGenerate结果、ai_plans.result，及页面editableTasks/generatedGoal | 从结果传入同一草案；无须先创建goals/tasks |
| 用户在原弹窗编辑后的版本 | 当前页面已有编辑能力，首次确认发布后还有按账号保存的待确认稿 | 保存/传递最新编辑版并标识版本；不能仍审核旧ai_plans.result |
| 用户已经发布的目标和任务 | goals及通过goal_id关联的tasks | 后端读取为审核快照，不改变正在执行的任务 |

总协调模式自动交接草案；独立审核入口建议让用户选择已有草案/目标，或从规划师点“交给审核师”。这些选择/传递入口目前尚未实现，不假设现有页面已有“草案库”。首版不必加入文件上传、任意文档解析等额外来源。

审核输入是“被检查的版本＋用户要求＋规则版本”，不能只有一段任务标题。编辑任务或更改时间预算后，旧审核结论需要失效。

## 4. 审核标准：现有校验、用户要求和模型评估

| 类型 | 具体依据 | 当前状态 |
|---|---|---|
| 已有业务硬校验 | 有效周期/日期、任务属于周期、1—20项任务、字段与长度、时长正整数且不超过1440、经验正整数且不超过1000等 | publishAiPlan已有；属于接口容许范围，不代表推荐用户安排这么长/这么高奖励 |
| 现有生成提示词 | 默认3—6项任务、10—30分钟、可量化可打卡、难度递进、经验10/20/30 | 提示词存在；不是每项都已由代码强制，也不能当通用用户标准 |
| 用户明确的硬约束 | 每天最多20分钟、仅周末可做、不能跑步等明确要求 | 应从聊天/设置获得；当前未形成完整结构化约束及校验链 |
| 候选产品规则 | 如何处理缺预算、休息日、重复任务、单项建议时长、修改后的复核 | 仍待共同确定，不能把助手建议当用户已确认规则 |
| 模型合理性评估 | 是否偏离目标、动作是否具体、对当前水平是否跨度过大、任务是否重复/含糊、阶段是否衔接 | 拟由Critic实现；应引用任务和约束说明问题，不编造权威评分 |

例如用户说每天20分钟，而某天安排两项15分钟任务：代码算出总计30分钟，指出超出10分钟；审核师再解释如何拆分更可执行。用户没提供每日预算时，只能说该项尚未验证或按明确标示的假设检查，不能声称“符合用户预算”。

建议审核输出采用“通过 / 需修改 / 信息不足”，包含任务定位、对应约束和修改建议，不先设计一个缺少依据的百分制。纯硬校验通过也不能冒充独立模型审核已经发生。

## 5. 教练/分析：已有业务记录具体有哪些

| 数据与获取位置 | 可用字段/含义 | 可支持的结论 | 不能据此断言 |
|---|---|---|---|
| goals，用户创建/发布/标记目标时保存 | title、状态、周期、起止日期、stages；部分旧记录字段缺失 | 目标是什么、当前状态、任务范围与阶段 | 单凭status=done证明现实技能已掌握 |
| tasks，通过创建任务/发布草案和打卡保存 | goal_id、title、date、stage、estimated_minutes、completed、较新记录的completed_at | 某目标某日期有几项安排、登记完成几项、预计负担、登记时间 | estimated_minutes是实际耗时；未打卡即未执行 |
| checkins和users签到字段 | date、created_at、streak_days等 | 每日签到频率、连续签到 | 等同目标连续完成天数或任务完成量 |
| growth_logs，任务/互动等奖励记录 | source、reason、xp_change、created_at；不同来源可能无统一task_id | 解释奖励来源、结合任务核对活动 | XP直接除以10就是完成任务数，或日志列表天然完整 |
| emotions，首页/情绪页提交 | 当天mood_index、mood_label、创建/更新时间 | 用户当天主动登记的心情 | 当前情绪日历/趋势为真实历史，或心情导致任务未完成 |
| ai_plans生成及发布快照 | planState、消息快照、result、来源/发布引用 | 关联的原规划上下文、当次计划假设及确认稿 | 拥有用户全部对话历史或完整的计划修改历史 |
| pets及必要互动记录 | 宠物性格/阶段、亲密度、成长与互动来源 | 为宠物伙伴提供真实经历背景 | 宠物mood代表用户心情，或喂养代表完成学习任务 |

任务是执行统计的主来源，奖励日志只作补充。每条读取都要绑定当前服务端身份，并限制目标/日期/必要字段。

### 当前记录的质量边界

- listTasks目前按单日并可带goal_id分页读取；没有现成的完整周复盘接口。需按目标及日期范围新增受控聚合能力，不能直接把dashboard.todayGrowth当近7天/累计数据。
- 较新taskCheckin保存completed_at，但它是服务器登记时间，补打卡时不代表实际做完的时间；旧数据可能缺该字段，精确时间统计应标记缺失。goal.completed_days是派生值，不替代原任务记录。
- 普通手动创建任务可能没有预计时长；不能默认为20分钟再当原始数据。当前数据没有稳定的原计划修改审计，不能凭现状还原过去每一天看到的完整计划。
- listGrowthLogs先safeQuery再排序/截默认50条，没有完整日期范围聚合/可靠全量分页保证。safeQuery还会把读失败转空数组；新统计工具必须区分无记录和读取失败，不能失败后输出0并作分析。
- 心情每日同账号同日会更新现有记录；不是完整日内轨迹。首页与情绪页的mood_index枚举不一致，应规范映射并保留来源，不能直接把索引当统一情绪分数。情绪页备注目前没随请求保存，日历/趋势是示例，均不能直接提供给教练作为事实。
- 现有“反馈”页面用于产品建议/Bug/内容问题，没有任务/目标关联，不是执行反馈采集入口。
- 番茄钟当前完成仅本地提示，没有持久的任务关联专注时段；不能据此计算真实专注总时长。

## 6. 缺少哪些反馈，怎样轻量获得

目前没有稳定保存的实际耗时、主观难度、未完成原因、兴趣变化、复盘意见；宠物聊天也还没有持久化的可反馈偏好记忆。

建议优先通过总协调/复盘聊天自然询问关键原因，例如“这几次主要卡在哪里？”；任务完成后的“轻松/刚好/吃力”或未完成任务的可选原因是后续候选，不强制每次打卡填问卷。

拟保存的最小关联信息为账号、goal_id、可选task_id、反馈对应日期/期间、用户原意或必要摘要、记录时间、来源。主观难度/阻力原因可选，实际分钟数也只能标为用户自报。长期偏好与短期心情分开，允许纠正，不让模型的原因推断自动成为反馈事实。

这些是待讨论的新采集能力，不是当前已保存的数据。第一版不需要等全部反馈采集完，先用任务记录做客观描述，原因不明就问用户。

## 7. 教练拿到的是代码统计的证据包

建议先按一个目标和明确期间（例如过去7个完整自然日）计算：安排/登记完成/未登记完成数量、完成率、每天预计负担、阶段分布、签到情况、有效心情记录、关联用户反馈及数据缺口。今天尚未结束的任务单列待完成，未来任务不加入过去完成率；0项任务应显示没有可统计任务而非满分。

期间任务数不是目标总周期的天数，也不意味着系统已给每天安排任务。时区统一Asia/Shanghai；记录登记时间、任务计划日期和反馈对应期间分开。

假设示例（不是云端数据）：过去7天安排10项、登记完成6项，用户反馈晚间任务偏累。代码先给出6/10和日期分布；Analyst可以说明近期有4项未登记完成，并结合用户自述提出调整时间的建议。不能仅凭6/10就声称发现懒惰、难度过高或已确定因果。无足够历史时提供冷启动说明，不造满一周记录。

## 8. 服务端数据工具与LangGraph交接（候选）

- getGoalContext：当前目标事实＋必要生成来源＋用户明确要求。
- getDraftSnapshot：取指定归属和版本的最新草案，不创建真实任务。
- getReviewEvidence：返回目标/期间的代码统计、相关记录引用、用户反馈和缺口。
- getCompanionContext：必要宠物/真实行为摘要，按允许范围带入偏好与心情。

以上是逻辑接口建议，尚不存在，不要求为每个工具新建云函数或复制一份数据库。图中通过状态引用同一快照，专业Agent只取需要部分；用户编辑或新数据改变关键输入时生成新版本，旧审核/复盘注明对应版本和期间。

实施先后建议：可靠提取并保存当前聊天要求和草案版本 → 读取既有任务做严格日期统计 → 最小用户反馈采集 → 再接复杂偏好记忆。数据与标准确定前不继续增加空泛角色。
