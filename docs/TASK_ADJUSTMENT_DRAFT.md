## 用户入口与边界

仍在森林管家“复盘调整”页，或从教练已有复盘精准跳转进入。增加“下一轮怎么安排？”卡片：明确本轮调整要求、可选每日预算 → 规划师给出变更 → 代码规则/独立AI审核 → 前后对照，允许编辑或逐项保留原安排。改稿保存新版本会使旧审核失效，用户再主动继续审核；没有确认应用按钮，不创建/修改正式目标任务或奖励。

服务器以北京时间计算明天起7天的窗口，一次最多20项已有、未删除且completed严格为false的任务。今天、历史、已完成和状态未知任务不纳入；目标已结束或已过周期则明确禁用，周期未知不凭空补造。记录超过上限保守阻止开始，不取部分任务冒充完整；没任务展示空状态，不调用模型补任务。名称、日期、预计分钟是唯一允许修改的业务字段，reason为说明；拒绝额外xp_reward/completed等字段、未知/重复task_id、越界日期和无效分钟。

用户本轮要求与可用时间明确保存；复盘取当前匹配的报告，可没有有效报告，此时只用代码事实/反馈/未来任务及本轮明确要求。没有把全局最新规划草案当成这个正式目标的要求。用户自述/任务文字是分析数据，不是系统指令。

## 技术实现

- adjustmentRules.js：稳定排序指纹、要求/白名单修改解析、全窗口每日预计负荷与明确预算检查、规划/独立审核提示词及引用任务ID检查。预计用时缺失保持未知；代码错误使AI审核跳过，主观语义建议不当成客观保证。
- adjustmentService.js：原生身份和目标归属、7天实际查询、源指纹、独立运行/草案版本、事务回执与单步fencing、持久化端口。仅ai_plans写入kind=adjustment_state，正文在payload，不占旧生成器result；生成/轮询/发布器不能当作计划来源。
- 原LangGraph图不改含义，新createAdjustmentGraph使用独立State/线程：manager → planner → rules → review → interrupt预览；改稿走manager → rules → review。复用ForestSaver和现有打包依赖，旧规划检查点兼容；新图线程包含运行ID/graph_revision，改稿不覆盖旧检查点。
- 5个action：getAdjustmentWorkspace、startAdjustment、stepAdjustment、saveAdjustment、cancelAdjustment。index.js仅惰性接入服务与既有模型适配；没有applyAdjustment。原规划师/独立审核师页面及原发布器均保留。
- 前端adjustmentWorkspace.js独立管理原目标/统计日期、输入缓存、前后对照、逐项拒绝、保存/恢复与版本冲突。不同账号/目标/日期隔离；本机稿保留最初编辑版本，不随刷新漂移。读云稿先备份，冲突不覆盖，副本可找回供核对；离开页停止自动推进，晚到响应不串目标/账号。

原发布器会生成新goal_id，因此不能复用为调整。旧审核规则以新目标草案为单位，这里使用窄的调整schema，复用日期/模型/持久化能力，不强行包装全局草案服务。正式任务应用留到5B专用事务。

## 版本、恢复与费用

来源指纹包括目标字段、未来任务原字段/状态及更新时间、教练事实/反馈指纹、可选有效复盘、当前业务日期/规则版本；对象键及任务顺序稳定规范化。读取是多查询快照而非跨集合原子快照；每次推进前重读，返回时再次核对，变化则不作为当前结论。调整前后不写tasks，所以没有把这层核对当成未来5B的写入保证；5B还必须事务内逐项检查确切版本/状态/日期。

开始/推进重复请求有确定性记录或回执，模型调用在事务外。新草案最多规划师+审核师各一次，每次函数最多一个模型步骤，18秒模型截止；无实际变更时跳过AI。错误不自动补模型调用，未知running先刷新，不自动抢占同一模型步骤重发；明确失败需新协作或用户改稿后主动审核。失败/超时仍可能计费。编辑后最多一次AI审核，保存/取消/刷新不调用模型。首版运行最多20次推进回执、最多10个草案版本，是保护上限，不承诺全部复杂草案在当前30秒配置内成功。

运行状态、模型步骤回执、版本化检查点和历史改稿分开；取消使token失效，晚到结果不能继续写。新运行成为同目标/日期head后，旧运行不能改稿或推进。所有历史均是自身ai_plans记录，版本体积超过限制会拒绝，不部分保存。
