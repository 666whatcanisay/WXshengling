# AI计划发布与恢复

2026-11-04，D021。用户在上一轮建议后要求继续；本轮完成本地发布可靠性，不部署、不操作真实用户数据。起点72e858e，分支codex/ai-plan-publication。

## 已实现

原流程由页面先建目标、逐项建任务，单项失败被忽略，仍可能提示成功；页面内Set也不能保证刷新或多次请求不重复。现新增app action `publishAiPlan`，业务集中在 `cloudfunctions/app/lib/planPublication.js`，普通手动目标/任务接口保留。

- 用现有ai_plans集合保存kind=plan_publication记录，不新增集合。先以小事务保存确认稿和publication_pending状态，再用一次事务写入目标、全部任务和publication_done回执。中断时可能留确认稿，但不会留下本轮半发布的目标/任务；重新提交相同请求可继续。
- 真实模型计划用服务端source_plan_id关联：首次发布验证来源属于当前微信调用者且生成已完成，同一来源跨请求/客户端仍定位同一发布。模板/调试计划使用持久化publication_id。所有ID均由服务端按调用者身份和来源计算，最终权限只信getWXContext的OPENID。
- 确认稿有指纹，已有发布不能用同一标识改写另一份内容；目标和任务采用确定ID。重复请求返回同一目标/任务回执，不重建、不复活已删除目标。已有回执不再依赖生成记录仍保留done状态。
- 页面在发请求前按当前账号保存待确认草稿；网络响应丢失、关闭弹窗或重新进入AI页后，显示“继续确认发布”。重试只提交原稿，确认成功后清缓存并跳转目标详情。保存失败则不开始发布；空/不完整响应不会假称成功。账号切换时隐藏上一账号待确认内容，迟到响应不跳转。
- 已提交稿暂时锁定编辑，避免结果未知时改稿再发。关闭按钮显示“稍后确认”，它不取消云端可能已完成的操作。调试全流程入口复用同一接口。

单次1至20项任务，时长1至1440分钟、经验1至1000整数、目标和任务标题最多200字；阶段和正文也有长度检查。这是应用为控制事务工作量设置的边界，不是平台限制。保留周期、日期、阶段和时长，AI发布不会另建同名初始任务。未升级依赖或加入Agent框架。

## 为什么这样实现

当前草案通常3至6项，首版用“短事务保存确认稿 + 有界事务整体发布”比逐任务补偿/隐藏半成品更小、更可靠。大规模排程再评估分批发布，不提前搭队列。[CloudBase官方事务说明](https://docs.cloudbase.net/database/transaction)要求注意执行时限和写冲突，故事务内没有模型/外部调用；20项的真实云端耗时尚未验证。

## 验证与边界

Node24.22.2下npm run verify通过：原41项业务回归、220项打卡/权限、163项发布检查，总计424项。新发布检查含26个后端/页面场景：20次重叠发布、无来源模板的账号隔离、来源归属/状态校验、目标/第二项任务/回执写失败与回滚、确认稿提交后中断、冲突耗尽后原请求恢复、回执丢失后的新页面恢复、存储失败、无效响应、编辑/会话重置保护、账号切换和20项边界。调用真实生产handler/Page和安装SDK，底层为离线传输替身。

37个生产JS语法检查、微信工具自带wcc的AI页WXML编译通过。证据见 `audit/ai-publication-20261104.json` 与 `audit/current-source-results-20261104-after-publication.json`。

未验证真实云事务隔离/锁/权限/时限、真机网络与真实模型；旧SDK部分文档操作冲突不能自动重试的限制保留，失败后用户可用原稿再次确认。历史重复目标、旧逐项发布的半成品不自动修补。旧客户端的独立createGoal/createTask调用也不会自动获得新发布保证。

本地恢复依赖同账号的设备缓存；清理缓存/换设备后，本轮没有跨设备的“待确认发布列表”。真实来源相同且请求内容相同时服务端仍能去重，模板丢失标识后不能保证恢复原请求。确认稿和回执不应作为普通临时生成记录随意清理，否则会失去去重依据。未知结果时没有强行取消/重新编辑功能；应先继续确认，确定性拒绝或损坏记录的处理可后续完善。
